# AGENTS.md

Guidance for AI agents (and humans) working in the **tile-upgrade-planner-muluna**
repository.

## What this project is

`tile-upgrade-planner-muluna` is a **Factorio 2.1 mod** that adds a selection tool
for planning tile upgrades. It is a fork of *Tile Upgrade Planner* maintained to
work with [Muluna](https://mods.factorio.com/mod/planet-muluna), but it does not
depend on Muluna and must work in a vanilla game too.

This is not a normal application: there is no build step, no server, and no
compiled artifact. The "code" is Lua that Factorio loads at specific **load
stages**, and the "output" is a zip published to the mod portal by CI.

- Language: **Lua 5.2** (Factorio's embedded interpreter).
- Requires: Factorio **2.1+**; Space Age is optional.
- Incompatible with the original `tile-upgrade-planner` (enforced by `info.json`).
- Version lives in `info.json` and is bumped by semantic-release. Localised text
  lives in `locale/en/en.cfg`.
- Mod portal: https://mods.factorio.com/mod/tile-upgrade-planner-muluna

There is a headless FUnit suite in
`test-mods/tile-upgrade-planner-muluna-funit/`. Run it before claiming a change
works. See [Testing](#testing).

## The Factorio load stages (most important concept)

Factorio runs a mod's Lua multiple times, exposing different globals each time.

1. **settings** — `settings.lua` / `settings-updates.lua` (none in this mod).
   Only `data` exists, for settings.
2. **data / data-updates / data-final-fixes** — `data.lua`,
   `data-final-fixes.lua`. `data.raw` and `data:extend` exist. `script`, `game`,
   `storage`, `prototypes` and `remote` do **not** exist here.
3. **control** — `control.lua` and `script/*`. `game`, `script`, `storage`,
   `prototypes`, `rendering` and `remote` exist. `data` does **not** exist here.

This mod shares state between stages with a `mod-data` prototype:

- `data.lua` sets `data.raw["mod-data"]["tile-upgrade-planner"].data = shared`.
- `script/gui.lua` and `script/planner.lua` read
  `prototypes.mod_data["tile-upgrade-planner"].data`.

`shared.lua` is the single source of truth for `names`, `tile_filters` and
`default_mapping`. Do not duplicate those values in data or control code.

## How the mod works

### Data stage

`data.lua` creates four prototypes with the same name, `tile-upgrade-planner`:

- a `selection-tool` (the item that is placed in the cursor),
- a `shortcut` (toolbar button),
- a `custom-input` (`SHIFT + ALT + U`),
- a `mod-data` bag that publishes `shared.lua` to runtime and to other mods.

The selection tool selects tiles (`tile-ghost`); alt-select removes tile ghosts.
`data-final-fixes.lua` currently only collects tile names and does not modify any
prototype. Its result is not used.

### Control stage

`control.lua` requires `script/gui.lua` and `script/planner.lua` in that order.
`script/gui.lua` registers `on_init`, which creates:

```lua
storage = {
    guis = {},                       -- [player_index] = open GUI root
    planner = {},                    -- [item_number] = array of {source=?, target=?}
    tasks = {front = 1, back = 1},   -- large-area queue
}
```

The planner configuration is stored per selection-tool instance by
`item_number`, so two planners can have different filters.

- `script/gui.lua` owns the GUI, `verify_filters` (drops tile names that cannot
  be placed by the current prototype set), and per-planner storage creation.
- `script/planner.lua` owns selection handling, the actual ghost creation, and
  the queue for selections larger than 100,000 tiles.
- `upgrade_area_for_force(force, surface, area, filters, player)` is the
  player-independent core. `upgrade_area(player_id, ...)` and
  `process_queue` resolve a player and call it.

Selection flow:

1. `on_player_selected_area` / `on_player_reverse_selected_area` copy the
   active planner's filters (reversing them for reverse-select).
2. Small areas are upgraded immediately; large areas are split into 1024-tile
   blocks and queued (`enqueue_area`).
3. `on_nth_tick(60)` drains one queued block per second.

The engine's behaviour is:

- For existing tile ghosts whose inner name is a mapping source, create a ghost
  for the target (unless the tile is already the target) and destroy the old
  ghost.
- For bare tiles whose name is a mapping source, create a target ghost unless a
  ghost already covered that tile.
- Unknown source tile names are ignored (prototype lookup filters them out).

## Public mod-data extension point

Other mods add tiles to the default planner by editing the published mod-data
table from their **data** stage:

```lua
table.insert(
  data.raw["mod-data"]["tile-upgrade-planner"].data.default_mapping,
  { source = "space-platform-foundation", target = "low-density-space-platform-foundation" }
)
```

Muluna does exactly this in
`planet-muluna/compat/tile-upgrade-planner-muluna.lua`. Keep this table and its
shape stable: it is the mod's public cross-mod API. The mod-data table must
exist in `data.lua` (before dependants run), not only in `data-final-fixes.lua`.

## Testing

The suite lives in `test-mods/tile-upgrade-planner-muluna-funit/` and is a
development-only companion mod. `.gitattributes` excludes `test-mods/`, this
file, `opencode.json`, `prompts/` and `tools/` from release zips.

### Running

```sh
# Base game only (no expansion mods active)
PROFILE=base bash test-mods/tile-upgrade-planner-muluna-funit/run.sh

# Space Age + Quality (enabled expansion mods)
PROFILE=space-age bash test-mods/tile-upgrade-planner-muluna-funit/run.sh

# Muluna + its dependencies from FACTORIO_MODS
PROFILE=muluna bash test-mods/tile-upgrade-planner-muluna-funit/run.sh
```

The default profile is `base`. The runner is headless and self-contained: it
links the current worktree as the mod, links the test mod and dependencies,
writes a scratch mod directory/config under `/tmp/opencode/...`, disables server
auto-pause, watches for FUnit's `====END====` line, and exits non-zero on any
`FAILURE` or `ERROR`. The full log is `$TMP_ROOT/stdout.log` and the FUnit JSON
report is under `$TMP_ROOT/write-data/script-output/`.

Useful environment variables: `FACTORIO_BIN`, `FACTORIO_MODS`, `PROFILE`,
`TMP_ROOT`, `TIMEOUT`, `FACTORIO_PORT`. See the test mod's `README.md` for
details.

CI (`.github/workflows/funit.yml`) runs the `base` and `space-age` profiles in
the `factoriotools/factorio:latest` image and converts the FUnit reports to
JUnit XML. The `muluna` profile is local-only because it needs a development
mod set.

### Layout

```
test-mods/tile-upgrade-planner-muluna-funit/
  data.lua, data-updates.lua, data-final-fixes.lua   fixture stage entry points
  lib/results.lua                                    records fixture results into mod-data
  prototypes/fixtures/                               data-stage checks (manifest lists stages)
  tests/helpers.lua                                  dedicated test surface + ghost helpers
  tests/manifest.lua                                 ordered runtime suite list
  tests/suites/                                      runtime behavior suites
  scenarios/__funit__tile_upgrade_planner/           FUnit scenario launcher
  run.sh                                             local headless runner
```

### How the two halves fit together

Data-stage checks cannot raise runtime FUnit failures directly. They run inside
`pcall` and record `{ok, err}` into the
`tile-upgrade-planner-funit-results` mod-data prototype. The runtime
`data_fixtures` suite asserts an **explicit expected ID list** from that bag, so
a fixture that stops recording an entry fails instead of disappearing from a
`pairs()` loop.

### Test-only seam

`script/funit.lua` is required from `control.lua` only when
`script.active_mods["funit"]` is set. It registers the
`tile_upgrade_planner_funit` remote interface and is inert in normal play. The
seam exposes:

- storage access (`get_storage`, `get_shared`), queue reset/enqueue/process,
- pure helpers (`verify_filters`, `get_filters`, `invert_table`, `area_size`),
- per-planner storage helpers (`ensure_planner`, `clear_planner`,
  `set_planner_target`),
- `upgrade_area_for_force` and `clear_area_for_force`.

Queued tasks accept an optional `force_name`; production never sets it. It lets
a headless test drive the queue because Factorio 2.1 has **no API to create a
player** (`game.create_player` does not exist). Do not invent fake players or
fake `LuaPlayer` tables.

### Coverage and limitations

Covered by the suite:

- final prototype contracts (selection tool, shortcut, custom input, sprites,
  mod-data payload, tile filters, default mapping, extension point),
- Muluna's compatibility insertion when Muluna is active,
- runtime storage initialization and runtime prototypes,
- filter conversion/validation, geometry, per-planner storage seeding,
- ghost creation for bare tiles, already-target tiles, existing source ghosts,
  invalid source names, reverse mappings, area-limited ghost clearing,
- queue splitting, upgrade processing, clear tasks, queue reset, stale-force
  tasks.

Not covered headlessly (verify manually in-game):

- the player cursor/GUI path (`on_player_cursor_stack_changed`, GUI element
  changes, add/remove row, open/close planner),
- the actual `start_selection`/selection-tool input path and reverse-select
  event wiring (`selected_area` itself is consumed by the force-level tests),
- `gvv` integration and cross-mod GUI mods.

Do not turn those into prototype-existence checks and call them covered.

### Instrument panel: keep the suite honest

- Every test must be capable of failing. No `assert(true, ...)`, no early
  `return`s that skip the body, no `pairs()` over "whatever exists".
- Use explicit fixture IDs and assert the expected IDs.
- Derive expected values independently; do not call the helper under test to
  compute its own expected result.
- Clean up entities, ghosts, queue state and planner storage even when an
  assertion fails. Use the dedicated test surface (`helpers.surface()`).
- Treat a new failure as a possible test bug first: check stage ordering,
  profile (`base` vs `space-age`), and setup before changing production code.
- If a test exposes a real bug, keep the test asserting the documented behavior
  and fix production code separately.

## Commits, changelog, and releases

Releases and `changelog.txt` are generated by `semantic-release` from commit
messages on `main` (see `.releaserc` and `.github/workflows/release.yml`). The
commit message is the changelog entry, so use Conventional Commits with this
project's custom types.

Format: `type: Summary sentence.` (optionally `type(scope): ...`). Examples:

```
fix: Fixed crash when reversing a tile upgrade without Muluna installed.
compat: Added Muluna's low-density space platform foundation to the default planner.
perf: Reduced work when processing large tile selections.
feat: Added a shortcut for the tile upgrade planner.
gui: ...
locale: ...
other: ...
```

`feat`/`feature` → minor; breaking → major; everything else (`fix`, `compat`,
`perf`, `gui`, `balance`, `graphics`, `locale`, `translate`, `control`, `other`,
`info`) → patch. Headings in `changelog.txt` come from the type. **Do not edit
`changelog.txt` or bump `info.json` by hand for a normal change** — CI does both.

Do not push to `main` without intending to release. The build agent's opencode
config denies `git push`.

## Factorio API docs helper

The `factorio-docs` agent answers questions from the Factorio prototype/runtime
JSON under `/opt/factorio_space_age_21/doc-html`. Use `tools/fdoc.py` instead of
ad-hoc `json.load()` snippets; it resolves prototype/class inheritance and
formats results readably:

```sh
python3 tools/fdoc.py --help
python3 tools/fdoc.py prototype tile-ghost
python3 tools/fdoc.py class LuaSurface --own-only
python3 tools/fdoc.py event on_player_selected_area
python3 tools/fdoc.py member set_tiles
```

The prompt in `prompts/factorio-docs.txt` points the agent at it. Trust the
documentation over model memory; read first, then answer.

## Working agreements

- Keep changes consistent with the surrounding 4-space Lua style.
- Preserve the `shared.lua` mod-data shape; other mods consume it.
- Guard optional mod behaviour with `if mods["..."]` (data stage) or
  `script.active_mods["..."]` (control stage).
- Do not touch `data.raw` in control code and do not touch `storage` in data
  code.
- Prefer the player-independent `upgrade_area_for_force` core when adding engine
  behavior; keep `upgrade_area`/`process_queue` as thin player resolvers.
- Never add a hard dependency on Muluna. Compatibility belongs in Muluna's
  `compat/` or in optional guards here.
- Run the base suite for every change and the space-age suite when touching
  prototypes or tile behavior. Run the muluna profile when changing
  compatibility.
- Do not "clean up" dead or commented code (`script/queue.lua`,
  `script/utils.lua`, `save_planner`, `update_label`, the commented blacklist,
  and the commented default-mapping entry) without understanding why it is
  there; several pieces are retained for save/edge-case reasons.

## Known quirks

- `planner.invert_table` returns an **array of the map's keys** (source tile
  names), not an inverted map. The name is historical; `upgrade_area_for_force`
  uses it as a name list for `find_tiles_filtered`.
- `item_index` is set to `0` for the first created ghost and `1` afterwards.
  Preserve it unless you have verified the engine semantics; it is legacy
  behaviour.
- Existing tile ghosts inside a selected area are destroyed even when their
  inner name is not a mapping source. This is current behaviour, not covered as
  a contract. If you change it, add a regression test.
- `script/queue.lua` and `script/utils.lua` are not required anywhere.
- `data-final-fixes.lua` builds a `tiles` table that is never used. Removing it
  is safe but unrelated to behavior changes.
